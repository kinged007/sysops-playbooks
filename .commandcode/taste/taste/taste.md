# Taste
- Prefers a "prepare the playbook, then run it, then test immediately" workflow for new infrastructure/service setup — build the asset, execute it end-to-end, and verify the result right away. Confidence: 0.85
- Expects a playbook-based, reusable structure for sysadmin/service setup (matching a `sysops-playbooks` repo with plan/runbook templates, notes, and scripts) rather than ad-hoc one-off setup. Confidence: 0.8
- Emphasizes that securing a service (environment keys, secrets, salts) is important and should be a first-class part of any setup playbook. Confidence: 0.9
- Wants the agent to generate random strings for all secret/salt environment values rather than using placeholder or user-supplied values. Confidence: 0.8
- Wants a durable record of what secrets were used kept in a dedicated `secrets/` folder so the user can audit them. Confidence: 0.85
- Prefers the agent to ask the user for deployment/access choices (e.g., install location — local/VPS/Docker — and the base URL / public URL where it will be reached) instead of silently assuming them. Confidence: 0.95
- Wants the agent to ask the user what they want at every playbook step rather than assuming defaults (e.g., never assume Docker); each step of the run should seek the user's input before proceeding. Confidence: 0.9
- Wants setup correctness verified by actually reaching and testing the published endpoints (e.g., curl the MCP/SSE status endpoint) rather than only assuming a successful install. Confidence: 0.85
- Wants playbooks to be written as generic, reusable frameworks that cover all installation possibilities with NO instance-specific data — the playbook outlines the options, and each run's real values live only in that run's `executions/<run>/` folder (plan/inventory/secrets), never in the committed playbook. Confidence: 0.9
- Requires authoring the playbook in full BEFORE running or testing it against any real instance — build the general asset first, then execute a run against it; never probe the target instance before the playbook exists. Confidence: 0.9
- Never prints, echoes, or logs secret/key values — only records and displays non-sensitive shape (byte length, line count, no-leading-comment check) and a short prefix (first ~8 chars); full values are read from the secrets file and used only in-memory. Confidence: 0.9
- Prefers the operator to drop secrets into the run's `secrets/` file and tell the agent the path (or have the agent read from it), rather than pasting raw secret values into chat; the agent verifies the file's shape before consuming it. Confidence: 0.75
- Prefers minimal, least-invasive writes during execution — do only the essential change needed to accomplish the goal (e.g., just enable MCP + set transport), and skip optional hardening/config rewrites unless explicitly requested. Confidence: 0.7
- When asked a direct binary question (e.g., "can you access the server or not?"), wants the direct answer stated first — a plain yes/no with the key fact — before any supporting evidence; long thorough summaries that bury or omit the specific answer are not wanted. Confidence: 0.65
- Wants the agent to consult the product's official skill/documentation (e.g., the OmniRoute `skills/omni-combos-routing/SKILL.md` on GitHub) when configuring or troubleshooting it, and wants that doc reference recorded in the playbook so it is fetched whenever the user asks about the product's capabilities. Confidence: 0.85
- Wants operational nuances/gotchas for handling a product (e.g., MCP being sessionful, correct endpoint probes, client-side quoting pitfalls) noted in the playbook/run notes before proceeding with configuration work — explicitly asks to "note the nuances" as a first step. Confidence: 0.8
- Wants configuration problems diagnosed by actually exploring the live system's state through its APIs (combos, providers, health/circuit breakers, metrics) and recording findings to logs, rather than theorizing from assumptions or docs alone. Confidence: 0.75
- During diagnosis, wants different failure hypotheses kept distinct (key-level vs account/model-level quota, 401 vs 403 vs 429) and the root cause confirmed empirically with a small real test call before making any write — even at the cost of a tiny bit of quota — rather than assuming from config alone. Confidence: 0.7
- For routing/combo configuration, prefers the preferred (top) model to be tried first with automatic fallback to other models/providers only on failure or quota exhaustion — accepts cost efficiency but not at the expense of model preference (e.g., prefers a priority-style strategy over a pure cost-optimizer that might skip the top model), and expects cost savings to come from provider-native prompt caching rather than a routing strategy that pins requests and breaks failover. Explicitly confirmed `priority` strategy and asked for a cross-provider safety-net fallback (e.g., `ollamacloud/deepseek-v4-flash`) appended after the same-provider model chain. Confidence: 0.85
- Wants optimization/compression strategies configured so that user-written long prompts are NEVER truncated, condensed, or summarised — the agent's full and complete understanding of the request is non-negotiable, and coding quality must not be degraded. Accepts (indeed prefers) that replies to the user are minimized/terse, with code blocks preserved byte-perfect. Explicitly chose to shield inputs completely (keep only tool-output compression) while enabling terse output styles. Confidence: 0.9
- Treats infrastructure isolation and least-privilege as first-class concerns in template/server design: flags any setup where one workspace/tenant can see or touch another's containers or the parent host daemon (e.g., root-equivalent Docker client certs exposing all host containers via `docker ps`) as a "major flaw," and wants isolation problems identified and mitigated rather than dismissed as inherent to the design. Confidence: 0.7
- Prefers template behavior to be parameterized with Terraform variables so the SAME template directory can be pushed under different configs (e.g., a `docker_enabled` boolean: enable Docker on one template push, lock it off on another; a template-level `startup_command` baked into every workspace's startup, running before per-workspace setup) rather than maintaining separate template copies — explicitly asked for "same template, different config" via `--var` flags, and for template-level (applies-to-all-workspaces) variables to be distinguished from per-workspace parameters. Confidence: 0.9
- Does NOT want the agent to push/upload artifacts to a live production system (e.g., `coder templates push`) without explicit approval — uploading is a production write against a live system; the agent should prepare the exact commands/config but wait for the user's go-ahead. Before preparing, ask for the required deployment parameters (server URL, template name, and all `--var` values) rather than assuming them. Confidence: 0.85
- Directs the agent to consult a prior run's `executions/` records (inventory, secrets, README) for live fleet connection/config details when performing a task (e.g., "see coder fleet current state in executions folder for connection") rather than re-asking for target/connection parameters already captured there. Confidence: 0.85
- Wants a clear boundary in production changes: the agent updates the template/infrastructure asset (e.g., `coder templates push`), while the operator updates their own workspaces themselves — explicitly "update the template there, not the workspaces; I will do that." The agent should not touch workspaces unless asked. Confidence: 0.8
- Prefers tooling/extension changes to be rolled out consistently across ALL template source families (e.g., when asked to add a VSCode extension preinstall, apply it to both `gvisor-docker` and `docker-devcontainer`) and pushed to every deployed fleet template the source maps to (all gVisor + dind), keeping the whole fleet uniform rather than scoping to only the template tied to the current task. Confidence: 0.65
